## Goal
Let an engineer create and list persisted alert subscriptions through the mobile API, rejecting subscriptions that name unknown services.

## Steps
1. Add a subscription model to `incidentdesk/models.py` with an identifier and the engineer, requested services, and minimum priority.
2. Add `POST /mobile/v1/subscriptions` and `GET /mobile/v1/subscriptions` to `incidentdesk/api/mobile.py`; validate every service against existing services, return the created subscription with its ID and status 201, and list subscriptions for the requested engineer.
3. Add subscription request and response schemas to `incidentdesk/schemas.py`.
4. Register the mobile router in `incidentdesk/app.py`.
5. Add `tests/api/test_mobile.py` cases for creating and listing subscriptions, returned IDs, and a 422 response for an unknown service.
6. Add a plain-language entry under `## Unreleased` in `CHANGELOG.md`.

## Tests
- The tests in `tests/api/test_mobile.py` verify a valid POST returns status 201 and the stored subscription fields with an ID.
- The tests in `tests/api/test_mobile.py` verify GET lists the subscriptions belonging to the requested engineer.
- The tests in `tests/api/test_mobile.py` verify an unknown service returns status 422 and does not create a subscription.
- Run `pytest tests/api/test_mobile.py` to check subscription persistence, validation, and response schemas.

## Risks
- The expected changes in `incidentdesk/api/mobile.py`, `incidentdesk/schemas.py`, `incidentdesk/app.py`, `tests/api/test_mobile.py`, and `CHANGELOG.md` overlap with #41 and #42. Coordinate integration of these changes because the three sessions use separate branches.
- `incidentdesk/models.py` is specific to #43. Validate service slugs before saving so an invalid subscription cannot be persisted.
- This sub-issue does not functionally depend on #41 or #42; merging the shared router, schema, app registration, test, and changelog edits does require coordination.

## Out of scope
- Incident listing and pagination from #41.
- Incident detail and timeline behavior from #42.
- The mobile API documentation requested separately in #44 and changes to the internal incident endpoints.
