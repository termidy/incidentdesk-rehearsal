## Goal
Expose a stable mobile endpoint that returns active incidents newest first in pages of 20, matching the response example in issue #41.

## Steps
1. Add `GET /mobile/v1/incidents` to `incidentdesk/api/mobile.py`, returning the mobile incident fields and `items`/`next_page` page envelope.
2. Add the mobile incident-list and page response schemas to `incidentdesk/schemas.py`.
3. Register the mobile router in `incidentdesk/app.py`.
4. Add `tests/api/test_mobile.py` cases for the response fields, active-incident filtering, newest-first order, 20-item pagination, and `next_page: null` on the final page.
5. Add a plain-language entry under `## Unreleased` in `CHANGELOG.md`.

## Tests
- The tests in `tests/api/test_mobile.py` verify the example response fields and that a page with another page available supplies its number in `next_page`.
- The tests in `tests/api/test_mobile.py` verify ordering, page size, and a null `next_page` when no further incidents exist.
- Run `pytest tests/api/test_mobile.py` to check the mobile list endpoint and its response schema.

## Risks
- The expected changes in `incidentdesk/api/mobile.py`, `incidentdesk/schemas.py`, `incidentdesk/app.py`, `tests/api/test_mobile.py`, and `CHANGELOG.md` overlap with #42; each file also overlaps with #43. Coordinate integration of these changes because the three sessions use separate branches.
- The example includes an acknowledged incident although the contract says “open incidents”; treat active as not resolved, and test that resolved incidents are excluded so acknowledged incidents remain eligible.
- This sub-issue does not functionally depend on #42 or #43; merging the shared router, schema, app registration, test, and changelog edits does require coordination.

## Out of scope
- Incident detail and timeline behavior from #42.
- Alert subscriptions and their persistence from #43.
- The mobile API documentation requested separately in #44 and changes to the internal incident endpoints.
