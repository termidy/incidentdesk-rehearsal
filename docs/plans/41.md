## Goal
Expose a stable mobile endpoint that returns open incidents newest first in pages of 20, matching issue #41's response example.

## Steps
1. Add `GET /mobile/v1/incidents` and its response schemas in the issue-owned router module `incidentdesk/api/mobile_incident_list.py`.
2. Add an issue-specific router import and `include_router` line in `incidentdesk/app.py`; both are needed to mount this router.
3. Add `tests/api/test_mobile_incident_list.py` for the response fields, open-incident filtering, newest-first order, 20-item pages, and `next_page: null` on the last page.
4. Add one plain-language line under `## Unreleased` in `CHANGELOG.md`.

## Tests
- `tests/api/test_mobile_incident_list.py` verifies the response example fields, ordering, page size, next-page number, and null next page.
- Run `pytest tests/api/test_mobile_incident_list.py`.

## Risks
- **Files owned by #41:** `incidentdesk/api/mobile_incident_list.py` and `tests/api/test_mobile_incident_list.py`.
- **Shared files touched:** `incidentdesk/app.py` (one issue-specific import line and one registration line) and `CHANGELOG.md` (one distinct entry). Keep these additions separate from #42 and #43 so the branches can merge without overwriting each other's lines.
- The example includes an acknowledged incident although the contract says “open”; interpret open as not resolved, and verify resolved incidents are excluded.
- #41 does not depend on #42 or #43.

## Out of scope
- Incident detail and timeline behavior from #42.
- Alert subscriptions from #43.
- Mobile API documentation requested separately in #44 and changes to internal incident endpoints.
