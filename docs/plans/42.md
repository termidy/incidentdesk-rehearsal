## Goal
Expose a stable mobile endpoint that returns an incident with its timeline in chronological order and the specified not-found response.

## Steps
1. Add `GET /mobile/v1/incidents/{key}` to `incidentdesk/api/mobile.py`, returning the mobile incident fields and timeline events oldest first; return HTTP 404 with `{"error":"not_found"}` for an unknown key.
2. Add the mobile incident-detail and timeline response schemas to `incidentdesk/schemas.py`.
3. Register the mobile router in `incidentdesk/app.py`.
4. Add `tests/api/test_mobile.py` cases for the response example, chronological timeline ordering, and the unknown-key status and body.
5. Add a plain-language entry under `## Unreleased` in `CHANGELOG.md`.

## Tests
- The tests in `tests/api/test_mobile.py` verify the example incident fields and timeline event shape.
- The tests in `tests/api/test_mobile.py` verify multiple timeline events are returned oldest first.
- The tests in `tests/api/test_mobile.py` verify an unknown key returns status 404 and `{"error":"not_found"}`.
- Run `pytest tests/api/test_mobile.py` to check the mobile detail endpoint and its response schema.

## Risks
- The expected changes in `incidentdesk/api/mobile.py`, `incidentdesk/schemas.py`, `incidentdesk/app.py`, `tests/api/test_mobile.py`, and `CHANGELOG.md` overlap with #41; each file also overlaps with #43. Coordinate integration of these changes because the three sessions use separate branches.
- A default FastAPI error body would differ from the contract’s mobile-specific error response; assert both status and exact JSON body.
- This sub-issue does not functionally depend on #41 or #43; merging the shared router, schema, app registration, test, and changelog edits does require coordination.

## Out of scope
- Incident listing and pagination from #41.
- Alert subscriptions and their persistence from #43.
- The mobile API documentation requested separately in #44 and changes to the internal incident endpoints.
